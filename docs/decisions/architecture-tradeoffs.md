# Архитектурные решения и компромиссы

Краткий журнал решений для последующего включения в README и резюме проекта.

## Гибридная интеграция с заведением

Авито.Кухня хранит локальную read-модель меню, а заведение остаётся источником
истины по фактической цене и возможности приготовить заказ.

**Почему:** каталог остаётся доступным и пригодным для поиска при временной
недоступности заведения, но окончательное подтверждение не опирается на
потенциально устаревшие остатки.

**Цена решения:** появляется eventual consistency. Меню версионируется, а заказ
до ответа заведения находится в `pending_confirmation`; изменение цены или
недоступность позиции не скрываются, а приводят к явному отклонению заказа.

## REST/JSON и OpenAPI вместо gRPC

Внешние контракты web-клиента и тестового заведения описываются OpenAPI 3.1 и
работают по HTTP/JSON.

**Почему:** это минимальный и прозрачный контракт для браузерного клиента,
партнёрской интеграции и Swagger UI. В задании OpenAPI является обязательным
артефактом.

**Цена решения:** нет строгой типизации gRPC-контракта между сервисами. Риск
компенсируется единой OpenAPI-схемой, контрактными тестами и возможной
кодогенерацией после стабилизации API.

## Два сервиса в одном репозитории

Основной сервис и пример заведения являются отдельными бинарниками и
контейнерами, но разрабатываются в одном Go-модуле.

**Почему:** выполняется требование задания, сохраняется простой локальный запуск
и можно явно продемонстрировать межсервисный контракт.

**Цена решения:** общий модуль упрощает случайное связывание реализаций. Общими
могут быть только нейтральные технические пакеты; бизнес-модели сервисов не
должны импортировать друг друга.

## PostgreSQL без брокера сообщений

На первом этапе используется одна PostgreSQL-инсталляция с отдельными базами
для сервисов. Надёжная доставка команд заведению в дальнейшем строится через
transactional outbox и фонового HTTP-worker, без Kafka.

**Почему:** outbox закрывает окно потери заказа между записью в БД и сетевым
вызовом, не добавляя тяжёлую инфраструктуру в MVP.

**Цена решения:** worker и повторные попытки всё равно требуют идемпотентности,
наблюдаемости и политики истечения подтверждения. При росте нагрузки outbox
можно подключить к брокеру без изменения доменного контракта.

## Асинхронное подтверждение заказа

Создание заказа возвращает `202 Accepted`, а начальный статус имеет значение
`pending_confirmation`.

**Почему:** сохранение заказа в Авито.Кухне ещё не означает, что заведение
подтвердило цену и наличие. API не создаёт ложной гарантии синхронного успеха.

**Цена решения:** web-клиент должен опрашивать состояние заказа. WebSocket/SSE
не входят в MVP и могут быть добавлены позднее без изменения state machine.

## Идемпотентность на каждой интеграционной границе

Клиент передаёт `Idempotency-Key`, основной сервис использует собственный
`order_id` при обращении к заведению, а callback-события имеют уникальный
`event_id` и монотонный `sequence`.

**Почему:** сетевые повторы являются нормальной ситуацией и не должны создавать
двойные заказы или повторные переходы состояния.

**Цена решения:** необходимо хранить ключи, hash исходного запроса и результаты
операций, а также определить срок хранения данных идемпотентности.

Callback-события одного заказа доставляются последовательно: пока событие с
меньшим `sequence` не завершено, следующее не может быть claimed worker-ом.
Это ограничивает параллелизм внутри одного заказа, зато platform никогда не
должна угадывать порядок по ненадёжному клиентскому времени. Разные заказы
по-прежнему обрабатываются параллельно bounded worker pool.

## Snapshot данных заказа

Название, цена и внешний идентификатор позиции копируются в строку заказа.
Деньги хранятся целым числом в минимальных единицах валюты.

**Почему:** изменение или удаление пункта меню не должно переписывать историю
заказа; целые значения исключают ошибки округления `float`.

**Цена решения:** часть данных дублируется намеренно и должна обновляться только
до фиксации заказа.

## Монотонная числовая версия меню

Venue service назначает каждой опубликованной версии меню возрастающий `int64`.

**Почему:** строковая версия позволяет проверить только равенство, но не даёт
однозначно определить устаревший snapshot. Числовая версия делает защиту от
out-of-order обновлений простой и детерминированной.

**Цена решения:** заведение обязано устойчиво хранить счётчик и увеличивать его
при каждом изменении меню. Версия не является временем и не должна вычисляться
из локальных часов.

## Отдельное состояние пользовательской отмены

Основной status описывает подтверждение и приготовление, а результат запроса
отмены хранится отдельно как `none/requested/confirmed/rejected/failed`.

**Почему:** единый status `cancellation_requested` скрывает фактическую фазу
приготовления и усложняет гонку между отменой и `start-preparing`.

**Цена решения:** модель заказа получает дополнительное поле и отдельные
переходы. Зато при неизвестном результате отмены платформа не выдаёт ложный
`cancelled` и сохраняет основной статус заказа.

Pending-заказ отменяется локально только пока confirmation outbox ещё не был
claimed. После dispatch запрос не маскирует неопределённость и возвращает
конфликт; после `accepted` используется отдельная идемпотентная команда. На
venue она и `start-preparing` блокируют одну строку заказа. Это оставляет короткое
окно, когда пользователь должен повторить действие после подтверждения, зато
исключает «успешную» отмену уже принятого и зарезервированного заказа.

## Осознанные ограничения MVP

В первую версию не входят оплата, курьеры, маршрутизация, промокоды, серверная
корзина, заказ из нескольких заведений, сложные модификаторы блюд, геополигоны,
точный ETA и пользовательская аутентификация. Партнёрское API при этом закрыто
статическими токенами из переменных окружения.

Ограничения уменьшают объём реализации, но не скрываются: они должны быть
описаны в README, а публичные контракты не должны обещать отсутствующие
гарантии.

## Статические service tokens и capability token заказа

Partner/platform/staff API используют разные статические Bearer tokens, а
публичное чтение и отмена заказа защищены отдельным случайным capability token.
Partner token на сервере связан с конкретным `venue_id`; выбрать чужое заведение
через JSON нельзя. Capability token генерируется через `crypto/rand`, клиент
получает его один раз, а слой хранения будет видеть только SHA-256 hash.

**Почему:** для MVP без пользовательских аккаунтов это даёт минимальный
контроль доступа, не смешивает роли и не требует OAuth/OIDC-инфраструктуры.
Ответ `404` для отсутствующего или неверного order token не раскрывает факт
существования заказа.

**Цена решения:** токены нельзя удобно отзывать и ротировать по отдельности,
нет идентичности конечного пользователя и аудита сессий. Для production
понадобятся secret manager, ротация и полноценная пользовательская
аутентификация; конфигурация уже запрещает `dev-*` secrets вне `local/test`.

## Общий нейтральный HTTP foundation

Оба сервиса переиспользуют только технические middleware: strict JSON,
problem details, request ID, CORS, recovery и access log. Transport DTO и
domain-модели при этом остаются раздельными для каждого bounded context.

**Почему:** единое поведение ошибок и observability снижает расхождения между
двумя API, не связывая их бизнес-модели.

**Цена решения:** shared-пакет становится внутренним контрактом двух сервисов.
Его намеренно ограничиваем HTTP-механикой; при появлении специфичных правил они
должны оставаться в соответствующем transport/application слое.

## pgxpool и явные транзакции без ORM

Каждый сервис открывает собственный ограниченный `pgxpool`. Repository работают
через небольшой `DBTX` interface, а атомарные сценарии — через явный
`WithinTransaction`; сам pool в business service не передаётся. Query timeout
задаётся PostgreSQL `statement_timeout` для каждого соединения.

**Почему:** pgx даёт нативную работу с PostgreSQL, context cancellation и
предсказуемые транзакции без скрытых запросов и mapping conventions ORM.

**Цена решения:** SQL и преобразование строк нужно писать вручную. Это больше
кода, зато query plans, locking и границы транзакций остаются видимыми — для
сценариев stock reservation и outbox это важнее скорости scaffolding.

## Одноразовые migration services

Перед запуском приложений Compose дожидается отдельных migration containers.
Версия и dirty state хранятся в каждой БД. Временный baseline step умеет
безопасно зарегистрировать старый локальный volume, созданный до появления
version table; неполную legacy-схему он отклоняет.

**Почему:** новые миграции применяются при каждом запуске и не зависят от
одноразового `/docker-entrypoint-initdb.d`.

**Цена решения:** в Compose появились четыре короткоживущих технических
контейнера. Baseline нужен только для совместимости текущих dev volumes и после
стабилизации проекта может быть удалён отдельным решением.

## Полный ограниченный menu snapshot вместо pagination

Список заведений использует непрозрачный cursor по стабильному внутреннему ID,
но меню возвращается одним snapshot с числовой версией. Размер входного snapshot
ограничен числом категорий и позиций, а общий HTTP body — конфигурационным лимитом.

**Почему:** cursor по элементам меню без snapshot isolation позволяет клиенту
получить первую страницу версии N, а следующую уже версии N+1. Цельный ответ
сохраняет простую гарантию: все категории и позиции относятся к одной версии.

**Цена решения:** очень большие меню потребуют большего ответа и не смогут
масштабироваться только увеличением числа страниц. Если лимиты MVP перестанут
подходить, контракт следует расширить immutable revision ID и cursor, закреплённым
за этой revision, либо выдавать подготовленный snapshot из object storage.

## Атомарный upsert с soft-delete

Платформа заменяет menu snapshot в одной транзакции: блокирует карточку venue,
проверяет version/hash, деактивирует прежние строки и upsert-ит присланные по
стабильным внешним ключам. Внутренние UUID существующих позиций сохраняются.

**Почему:** заказы ссылаются на внутренние ID, поэтому физическое удаление или
пересоздание позиции ломало бы историю. Транзакция не позволяет читателю увидеть
частично обновлённое меню.

**Цена решения:** таблицы накапливают неактивные строки, а полная замена имеет
стоимость O(размер меню). Для крупных каталогов понадобятся retention/archive и
инкрементальный протокол поверх той же модели версий.

## Синхронная публикация меню при старте venue

Тестовое заведение читает собственное меню из PostgreSQL и при старте публикует
полный snapshot и доступность в partner API. Запуск ограничен общим timeout;
ошибка публикации завершает процесс, чтобы контейнер не выглядел готовым при
несогласованном каталоге.

**Почему:** для одного демонстрационного venue это короткий и наблюдаемый путь к
воспроизводимому `docker compose up`, а точный повтор snapshot идемпотентен.

**Цена решения:** недоступность platform задерживает старт venue, публикация не
реагирует на изменения после запуска и пока не имеет фоновых retry. Production-
вариант потребует outbox/change worker с backoff, jitter и метриками доставки.

## Воспроизводимый tracking token для идемпотентного checkout

Tracking token детерминированно выводится через HMAC-SHA-256 из server secret и
scope `(customer_ref, Idempotency-Key)`. В PostgreSQL по-прежнему хранится только
SHA-256 hash токена; открытый token можно повторно получить только при точном
идемпотентном повторе исходного checkout.

**Почему:** требования «не хранить открытый token» и «вернуть прежний результат
при retry» несовместимы со случайным невосстановимым token. HMAC сохраняет оба
свойства без хранения дополнительного секрета на каждый заказ.

**Цена решения:** безопасность зависит от отдельного сильного
`ORDER_TOKEN_SECRET`; его компрометация позволяет вычислять tokens при известных
customer/key. В production secret должен храниться в secret manager и
ротироваться с поддержкой версии ключа.

## Пессимистическое резервирование остатков в venue

Venue сериализует конкурирующие заказы через `SELECT ... FOR UPDATE` по строкам
меню и сохраняет решение в той же транзакции, где уменьшает конечный остаток.
Повтор по `platform_order_id` возвращает сохранённое первое решение.

**Почему:** это простая строгая гарантия, что последнюю единицу нельзя продать
дважды и сетевой retry не резервирует её повторно.

**Цена решения:** горячие позиции становятся точкой lock contention, а порядок
блокировок должен оставаться детерминированным. При высокой нагрузке можно перейти
к условному atomic update или отдельному inventory ledger, сохранив внешний
идемпотентный контракт.

## PostgreSQL outbox claim с короткой lease

Несколько platform workers атомарно забирают готовые jobs через
`FOR UPDATE SKIP LOCKED`, записывают `lock_token/locked_until` и освобождают
транзакцию до HTTP-вызова. Ответ применяется только владельцем актуальной lease.

**Почему:** сетевой I/O не удерживает DB locks, workers масштабируются ограниченным
пулом, а зависшая после падения job автоматически становится доступной после
lease. Идемпотентность venue закрывает окно «ответ получен, processed не записан».

**Цена решения:** доставка остаётся at-least-once, порядок между разными заказами
не гарантируется, а параметры lease/backoff требуют операционной настройки.
Долгий HTTP timeout должен всегда быть короче lease.
