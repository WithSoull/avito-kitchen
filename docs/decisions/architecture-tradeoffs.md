# Архитектурные решения и компромиссы

Здесь перечислены только решения, у которых есть заметная цена или
альтернатива. Требования задания — Go, Docker Compose, OpenAPI и отдельный venue
service — не выдаются за архитектурные решения.

## Локальная копия меню, окончательное решение у venue

Platform хранит меню для каталога и checkout, поэтому чтение не зависит от
доступности venue. При подтверждении venue повторно проверяет версию, цену и
остатки.

Цена — eventual consistency между двумя базами. Заказ может пройти локальную
проверку platform и позже получить `menu_changed` или `items_unavailable`.
Убирать повторную проверку нельзя: platform не владеет фактическими остатками.

## Меню передаётся полным snapshot

Venue публикует всё меню одним `PUT` с возрастающей числовой версией. Platform в
одной транзакции обновляет категории и позиции, а отсутствующие записи помечает
неактивными. Повтор версии с тем же payload идемпотентен; другой payload с той же
версией считается конфликтом.

Это проще частичных обновлений и позволяет однозначно обнаруживать устаревшую
версию. Цена — размер запроса ограничен возможностями одного HTTP-вызова и одной
транзакции. Для MVP установлены пределы на число категорий и позиций. Большому
каталогу потребовался бы change feed или разбиение snapshot на части с отдельным
протоколом публикации.

Публичное чтение меню выполняется в read-only `REPEATABLE READ`: версия,
категории и позиции читаются из одного MVCC snapshot. Без этого несколько
последовательных SELECT в `READ COMMITTED` могли смешать данные двух версий.

## Заказ и исходящая команда сохраняются атомарно

Checkout не вызывает venue синхронно. Platform одной транзакцией создаёт заказ,
snapshot позиций, историю и `confirm_order` в outbox, затем возвращает
`202 Accepted`.

Это закрывает окно «заказ записан, но команда потеряна до отправки». Цена —
клиент должен опрашивать статус, а доставка становится at-least-once. Получатель
обязан хранить стабильное решение и корректно обрабатывать повторы.

Worker захватывает job через `FOR UPDATE SKIP LOCKED`, выдаёт ей короткую lease
и делает HTTP-вызов после завершения транзакции claim. Старый worker не может
применить ответ после потери lease благодаря `lock_token`.

## Outbox не устраняет неопределённый удалённый результат

Если venue успело сохранить `accepted` и уменьшить остаток, но HTTP-ответ был
потерян, platform не знает результат. Повтор команды обычно возвращает
сохранённое решение, однако текущий worker прекращает попытки после deadline или
лимита retries. Тогда platform записывает `confirmation_expired`, а venue может
сохранить заказ и резерв.

Outbox гарантирует повторяемую доставку локально сохранённой команды, но не
атомарность двух баз и не exactly-once.

Варианты исправления:

- продолжать фоновую reconciliation после пользовательского deadline и добавить
  callback с решением от venue;
- использовать временный резерв с TTL и отдельное подтверждение резерва.

Для текущего проекта предпочтительна reconciliation: она использует уже
существующую идемпотентность и требует меньше новых состояний. Поздний
`accepted` следует компенсировать отменой, потому что пользователь уже мог
повторить заказ. Реализация этого протокола пока отсутствует.

## Идемпотентность хранится в базе

Публичный checkout дедуплицируется по `(customer_ref, Idempotency-Key)` и hash
нормализованного запроса. Тот же ключ с другим телом возвращает конфликт. Venue
хранит первое решение по `platform_order_id`, callback — по `event_id` и
`sequence`.

До появления строки заказа одинаковые запросы сериализуются
`pg_advisory_xact_lock`. Уникальные ограничения остаются последней защитой.

Цена — ключи и результаты нельзя удалить раньше максимального срока возможного
retry. Политика retention в MVP не реализована.

## Остатки блокируются пессимистически

Venue читает запрошенные позиции через `FOR UPDATE` в стабильном порядке,
проверяет количество и уменьшает stock в той же транзакции, где сохраняет
`accepted`.

Так последняя единица не достанется двум конкурентным заказам. Цена — популярная
позиция становится точкой конкуренции за lock. Для нагрузки выше MVP можно
перейти к условному `UPDATE ... WHERE stock_quantity >= quantity` или inventory
ledger, сохранив внешний идемпотентный контракт.

## Заказ хранит snapshot позиции и цену

`order_items` содержит внешний ID, название, количество и цену на момент
checkout. Исторический заказ не меняется вслед за меню. Деньги хранятся в
`bigint` в минимальных единицах валюты, без `float`.

Цена решения — дублирование данных. Оно намеренное: ссылка на текущее меню не
может быть единственным источником исторической цены.

## Отмена имеет отдельное состояние

Основной `status` показывает стадию заказа. Результат пользовательской отмены
хранится отдельно в `cancellation_status`: `none`, `requested`, `confirmed`,
`rejected`, `failed`.

Это позволяет не скрывать `accepted` или `preparing`, пока результат удалённой
отмены неизвестен. Цена — две связанные машины состояний. Venue сериализует
отмену и `start-preparing` блокировкой одной строки, поэтому только одна команда
побеждает гонку.

Pending-заказ отменяется локально только до первого claim confirmation job.
После dispatch platform не может достоверно утверждать, что venue ещё не начало
обработку.

## Tracking token вместо пользовательской аутентификации

Пользовательской учётной записи в MVP нет. При checkout клиент получает
непредсказуемый без знания server secret tracking token; в БД хранится только
SHA-256 hash. Token детерминирован для `(customer_ref, Idempotency-Key)`, чтобы
точный повтор checkout вернул прежнее значение. Неверный token и неизвестный
заказ возвращают одинаковый `404`.

Это дешевле полноценной auth-системы, но потерянный token нельзя восстановить.
Компрометация `ORDER_TOKEN_SECRET` позволяет вычислять детерминированные tokens
для известных idempotency keys, поэтому production-поставка потребовала бы
secret manager и версионирования ключей.

Partner, platform и staff API используют разные статические Bearer tokens. Это
приемлемо для одного демонстрационного venue, но не решает выдачу, ротацию и
отзыв credentials для множества заведений.

## Синхронная публикация меню при старте venue

Venue публикует меню и доступность до запуска HTTP listener. Так ready процесс
не обслуживает заказы с ещё не синхронизированным меню.

Цена — недоступная platform мешает старту venue. Для независимого запуска нужен
локальный publisher outbox и отдельная readiness-политика. Для одного Compose
окружения синхронный вариант проще и наблюдаемее.

## Миграции как отдельные Compose services

Приложения не выполняют DDL при старте. Одноразовые `migrate-platform` и
`migrate-venue` завершаются до запуска сервисов; readiness проверяет ожидаемую
версию схемы.

Это исключает гонку нескольких экземпляров приложения за миграцию. Цена —
оркестратор должен правильно упорядочить migration job и runtime. Legacy
baseline нужен только для старого локального volume и не заменяет versioned
migrations.
