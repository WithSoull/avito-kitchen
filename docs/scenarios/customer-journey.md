# CJM пользователя Avito.Kitchen

Документ фиксирует продуктовый сценарий web-клиента до реализации
бизнес-логики. Code-generated диаграмма по этому сценарию будет добавлена на
этапе 12 roadmap.

## Границы MVP

- Клиентская часть и пользовательская аутентификация не реализуются.
- `customer_ref` связывает заказ с пользователем основной платформы, но не
  используется как доказательство личности.
- Доступ к конкретному заказу защищает случайный `tracking_token`.
- Корзина живёт в браузере и содержит позиции только одного заведения.
- Все заведения находятся в одной тестовой зоне доставки.
- Единственная валюта — `RUB`; суммы передаются в копейках целым числом.
- Оплата, курьеры, промокоды, ETA и модификаторы блюд не входят в MVP.

## Основной сценарий

### 1. Найти заведение

Клиент вызывает:

```http
GET /api/v1/venues?query=пицца&limit=20
```

Платформа возвращает только активные заведения и показывает, принимает ли
каждое из них заказы. Cursor используется для следующей страницы.

### 2. Посмотреть меню

```http
GET /api/v1/venues/{venue_id}/menu
```

Ответ содержит категории, доступные позиции, цены, валюту и `menu_version`.
Меню является локальной read-моделью платформы и может кратковременно отставать
от состояния заведения.

### 3. Собрать корзину

Web-клиент хранит корзину локально. При попытке добавить позицию другого
заведения клиент предлагает очистить текущую корзину. Сервер всё равно проверяет
инвариант «один заказ — одно заведение» при checkout.

Клиент не является источником истины для цены: он отправляет только ID позиции
и количество.

### 4. Создать заказ

```http
POST /api/v1/orders
Idempotency-Key: <client-generated-unique-key>
Content-Type: application/json
```

Запрос содержит `customer_ref`, `venue_id`, просмотренную `menu_version`,
позиции, телефон и адрес доставки.

Платформа:

1. Валидирует формат запроса и бизнес-инварианты.
2. Пересчитывает цену по своей копии меню.
3. В одной транзакции создаёт заказ `pending_confirmation`, snapshot позиций,
   историю и outbox-команду заведению.
4. Возвращает `202 Accepted`, `order_id` и открытый `tracking_token`.

Клиент сохраняет `tracking_token`; платформа хранит только его hash. Потерянный
токен восстановить нельзя в рамках MVP.

### 5. Дождаться подтверждения

```http
GET /api/v1/orders/{order_id}
X-Order-Token: <tracking_token>
```

Клиент выполняет polling с разумным интервалом. Возможные результаты:

- `pending_confirmation` — заведение ещё не приняло решение;
- `accepted` — цена и возможность приготовить подтверждены;
- `rejected` — заведение отказало с безопасной причиной;
- `confirmation_expired` — подтверждение не получено за отведённое время.

Пользователь никогда не видит внутренние номера попыток, outbox и сырые ошибки
интеграции.

### 6. Отслеживать приготовление

После принятия заказ последовательно проходит:

```text
accepted → preparing → ready → completed
```

Статусы присылает заведение, платформа проверяет порядок и разрешённость каждого
перехода.

### 7. Отменить заказ

До первого claim confirmation job pending-заказ можно отменить локально: он не
попадёт в venue, а его основной статус сразу станет `cancelled`. После dispatch
отмена ожидает окончательного решения. Для `accepted` заказа, пока заведение не
начало приготовление:

```http
POST /api/v1/orders/{order_id}/cancel
X-Order-Token: <tracking_token>
```

Платформа выставляет отдельный `cancellation_status=requested`, не скрывая
основной `status=accepted`, и отправляет идемпотентную команду заведению.

Результаты:

- `confirmed` и основной статус `cancelled` — резерв освобождён;
- `rejected` и основной статус `preparing` — отмена проиграла гонку началу
  приготовления;
- `failed` — платформа не смогла получить достоверный результат; основной
  статус сохраняется и требуется повтор/операционное разрешение.

Если confirmation job уже был claimed, но решение ещё не записано, отмена
возвращает `409 ORDER_CANCELLATION_NOT_ALLOWED`: платформа не делает вид, что
может безопасно отозвать уже отправленную команду.

## Негативные сценарии

| Ситуация | Поведение API | Что видит пользователь |
|---|---|---|
| Заведение закрыто до checkout | `409 VENUE_CLOSED` | Заказ не создан, нужно выбрать другое заведение |
| Клиент прислал старую версию меню | `409 MENU_CHANGED` | Обновить меню и подтвердить новую корзину |
| Цена изменилась только в заведении | Заказ создаётся, затем становится `rejected` с `menu_changed` | Обновить меню и оформить заново |
| Позиция закончилась | Заказ становится `rejected` с `items_unavailable` | Убрать недоступные позиции |
| Заведение временно недоступно | Заказ остаётся `pending_confirmation`, выполняются ограниченные retries | Ожидание, затем результат или `confirmation_expired` |
| Заведение не ответило до deadline | `confirmation_expired` | Заказ не принят, повторное оформление — новый заказ |
| Двойной клик checkout | Возвращается первый заказ по тому же `Idempotency-Key` | Один заказ |
| Тот же ключ с другим телом | `409 IDEMPOTENCY_KEY_REUSED` | Клиент генерирует новый ключ для нового намерения |
| Неверный `tracking_token` | Такой же `404 ORDER_NOT_FOUND`, как для неизвестного ID | Никакие данные заказа не раскрываются |
| Отмена после начала приготовления | `409 ORDER_CANCELLATION_NOT_ALLOWED` | Заказ продолжает готовиться |
| Callback пришёл повторно | Идемпотентный `204` | Статус не дублируется |
| Callback пришёл не по порядку | `409 EVENT_SEQUENCE_CONFLICT` | Последнее корректное состояние сохраняется |

## Критерии готовности пользовательского CJM

- Все шаги выполняются только через публичное API платформы.
- Пользователь не обращается напрямую к venue service.
- Ни один бизнес-отказ не возвращается как случайный `500`.
- Цена в созданном заказе является неизменяемым snapshot.
- Повторы checkout и polling безопасны.
- Без tracking token нельзя прочитать или отменить заказ.
